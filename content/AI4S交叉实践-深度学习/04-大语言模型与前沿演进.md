## 1. 混合专家模型（Mixture of Experts, MoE）

> MoE 的核心思想：用大量专家构建知识池，通过路由为每个 Token 只激活少数专家，实现**容量与算力的解耦**。


### 1.1 为什么需要 MoE

### 1.1.1 传统稠密模型的瓶颈

稠密模型中，所有参数对所有 Token 都参与计算。想提升模型能力就必须增加参数，而参数增加导致计算成本同步暴涨。

### 1.1.2 MoE 的核心理念

$$
\text{MoE} = \text{许多专家} + \text{一个路由器}
$$

- **总参数量（Total Parameters）**：极大 → 知识容量大
- **激活参数量（Active Parameters）**：极小 → 每个 Token 只激活少数专家，计算成本低

> MoE 解耦了容量与算力：总参数量可以很大，但实际计算量只与激活参数成正比。


### 1.2 前沿 MoE 模型对比

| 模型 | 时间 | 总参数 | 激活参数 | 专家数 | Top-k |
|------|------|--------|---------|-------|-------|
| Kimi K2 | 2025-07 | 1 T | 32 B | 384 | 8 |
| Qwen3.5-397B-A17B | 2026-02 | 397 B | 17 B | 512 | 10 |
| **DeepSeek-V4-Pro** | 2026-04 | **1.6 T** | **49 B** | 384 | 6 |
| GLM-5.2 | 2026-06 | 744 B | 40 B | 256 | 8 |

激活参数通常仅占总参数的 **2%~5%**。


### 1.3 参数量计算（以 DeepSeek-V4-Pro 为例）

核心超参数：专家总数 385（1 共享 + 384 路由），Top-6，58 层，隐藏层维度 7168，专家中间维度 3072。

### 1.3.1 MoE 总参数量

$$
58 \times 7168 \times 3072 \times 3 \times 385 \approx 1.48 \text{ T}
$$

`3` 对应 SwiGLU 的三个权重矩阵（$W_{gate}, W_{up}, W_{down}$）。

### 1.3.2 MoE 激活参数量

$$
58 \times 7168 \times 3072 \times 3 \times 7 \approx 26.8 \text{ B}
$$

每次激活 1 个共享专家 + 6 个路由专家 = 7 个专家。

### 1.3.3 路由器参数量

$$
58 \times 7168 \times 384 \approx 0.16 \text{ B}
$$

路由器本身非常小，相比于专家参数可以忽略不计。


### 1.4 FFN 回顾

标准的 Transformer FFN：

$$
\text{FFN}(x) = W_2 \sigma(W_1 x), \quad d \to 4d \to d
$$


![[Pasted image 20260708201342.png]]

- **Attention**：不同 Token 之间交互信息
- **FFN**：同一 Token 不同通道间信息转换
- FFN 占模型总参数的约 **2/3**
- FFN 对每个 Token **独立并行计算**

MoE 的本质：将固定的 FFN 替换为多个"专家 FFN"组成的资源池。


### 1.5 MoE 前向传播

### 1.5.1 三步走

**Step 1：专家打分**

$$
s = W_g x, \quad W_g \in \mathbb{R}^{N \times d}
$$

路由器计算 Token 与每个专家的契合度得分。

**Step 2：选择 Top-k 并计算权重**

$$
g_i = \frac{e^{s_i}}{\sum_{j \in \text{Top-}k} e^{s_j}}
$$

只对选中的 $k$ 个专家做 Softmax 归一化，其余归零。

**Step 3：加权组合输出**

$$
y = \sum_{i \in \text{Top-}k} g_i E_i(x)
$$

各专家输出加权求和。

![[Pasted image 20260708201423.png]]

### 1.5.2 路由器训练

- 路由器权重 $W_g$ 通过**反向传播**与整个模型一同训练
- 语言模型损失经 $y = \sum g_i E_i(x)$ 回传梯度
- 若某专家帮助降低 Loss，其得分被**强化（Reinforce）**
- 需引入**负载均衡损失**防止路由崩溃


### 1.6 负载均衡：防止路由崩溃

### 1.6.1 路由崩溃（Routing Collapse）

路由器天然存在"富者更富"的马太效应：某几个专家被选中的次数多 → 训练数据更多 → 能力更强 → 被选中的次数更多。最终少数专家承载所有 Token，其余专家闲置。

### 1.6.2 负载均衡损失

$$
\mathcal{L}_{\text{lbl}} = \frac{E}{k} \sum_{e=1}^E f_e P_e, \quad
f_e = \frac{1}{T} \sum_{t=1}^T \mathbf{1}(\text{token } t \text{ selects expert } e), \quad
P_e = \frac{1}{T} \sum_{t=1}^T s_{e,t}
$$

其中 $s_{e,t}$ 是路由器给 Token $t$ 分配到专家 $e$ 的 Softmax 概率（连续可导），$f_e$ 是实际分配到专家 $e$ 的 Token 比例（由指示函数计数，不可导），$P_e$ 是路由器给专家 $e$ 的平均概率期望（可导）。

$f_e \times P_e$ 的设计精妙之处在于：$f_e$ 保证惩罚与实际负载挂钩（防止路由器靠打高分但实际不分配来作弊），$P_e$ 负责传导梯度让路由器学会调整。

$\mathcal{L}_{\text{lbl}}$ 作为辅助损失加入总损失函数：

$$
\mathcal{L}_{\text{total}} = \mathcal{L}_{\text{LM}} + \alpha \mathcal{L}_{\text{lbl}}
$$

其中 $\alpha$ 通常设得很小（如 0.01）。反向传播时，梯度的 $\alpha \nabla \mathcal{L}_{\text{lbl}}$ 部分通过 $P_e$ 回传给路由器，压低热门专家的分数，把流量推给冷门专家。

系数 $\frac{E}{k}$ 的作用是归一化，使均匀分配时 $\mathcal{L}_{\text{lbl}} = 1$：完全均匀下各专家 $f_e = k/E$、$P_e = 1/E$，代入得 $\mathcal{L}_{\text{lbl}} = 1$（由排序不等式 $\sum f_e P_e \ge k/E$，均匀时取最小值）。没有 $\frac{E}{k}$ 时均匀分配的损失会随 $E$ 和 $k$ 变化，无法跨模型统一比较。


### 1.7 代码草图

```python
### 1.7.1 路由与门控
scores = router(x)                     # [tokens, n_experts]
vals, ids = scores.topk(k, dim=-1)    # 选 Top-k
gates = vals.softmax(dim=-1)          # 门控权重

### 1.7.2 专家计算（遍历专家，不遍历 Token）
y = torch.zeros_like(x)
for e, expert in enumerate(experts):
    mask = (ids == e)                 # 找出分配给该专家的 Token
    if mask.any():
        token, slot = mask.nonzero(as_tuple=True)
        y[token] += gates[token, slot, None] * expert(x[token])
```

**核心工程原则**：不要遍历 Token，要去遍历专家。把每个专家的 Token 收集起来打包成稠密批次运行，充分利用 GPU 并行能力。


### 1.8 基础设施：专家并行（Expert Parallelism, EP）

### 1.8.1 通信流程

| 阶段 | 操作 | 通信 |
|------|------|------|
| **Dispatch**（分发） | All-to-All | 将 Token 发送到拥有目标专家的 GPU |
| **Compute**（计算） | 本地稠密批处理 | 无需跨卡通信 |
| **Combine**（合并） | All-to-All | 将计算结果送回原始 GPU |

### 1.8.2 两种切分策略

| 规模 | 每 GPU 专家数 | 通信压力 |
|------|-------------|---------|
| 小规模 | 多专家/GPU | 小 |
| **大规模** | **少专家/GPU** | **大（瓶颈）** |

大规模 EP 时，几乎所有 Token 都需要跨卡通信，All-to-All 成为系统性能瓶颈。


### 1.9 单卡优化：GroupedGEMM

MoE 的计算分散在各个专家上，每个专家只分到少量 Token（比如 32 个专家平分 128 个 token，每个专家只有 4 个 token）。这就产生了一大堆**小矩阵乘法**——形状 (4, d) × (d, 4d) 这种。

GPU 跑大矩阵乘法效率很高，但跑小矩阵有个隐藏开销：**Kernel Launch**。

每一次执行 `torch.mm(A, B)`，CPU 都要往 GPU 的命令队列里塞一条指令："现在执行一个矩阵乘法，参数是 A 和 B"。CPU 塞这条指令大约需要 10~50μs。对于大矩阵来说这个开销可以忽略（一次 GEMM 跑几 ms），但对于小矩阵，计算本身可能只要十几 μs，Kernel Launch 的开销就占了大头。

**普通做法**——循环启动 32 个 Kernel：

```python
for e in range(32):
    y[e] = expert[e](x[e])     # CPU 塞一条命令 → GPU 执行 → 塞下一条 → 执行……
```

32 次启动 = 32 × ~20μs = ~640μs 纯开销，**GPU 在这期间间歇空转**。

**GroupedGEMM**——把 32 个小 GEMM 打包成 1 次 Kernel 启动：

```python
grouped_gemm([x0,...,x31], [W0,...,W31])   # CPU 只塞 1 条命令
```

GPU 收到命令后，内部依次处理 32 个专家，中间不需要 CPU 反复介入。

| | 普通做法 | GroupedGEMM |
|:--|:--------|:-----------|
| CPU→GPU 指令数 | 32 条 | 1 条 |
| Kernel Launch 开销 | ~640μs | ~20μs |
| Tensor Cores 利用率 | 低（频繁中断） | 高（连续喂数据） |

> 类比：老板（CPU）指挥工人（GPU）搬 32 堆砖。普通做法是每搬一堆就说一次"搬这堆"，说 32 次；GroupedGEMM 是一次性说"把 32 堆全搬了"，工人自己依次搬完。搬砖时间一样，但"张嘴说话"的时间从 32 次减到 1 次。


### 1.6 路由翻转（Routing Flip）与 ReMoE

传统 Top-$k$ 中专家激活是**分段常数**函数——当专家得分接近时，权重的微小更新会导致选中专家集合突变，训练震荡。

**ReMoE** 的解决方案：去掉 Top-$k$ + Softmax，替换为 ReLU：

$$
R(x) = \text{ReLU}(W_g x)
$$

- 专家激活随得分平滑连续变化，无断崖跳变
- 用自适应 $\ell_1$ 惩罚控制激活专家数量，保持稀疏性


### 1.11 关键术语速查

| 术语 | 含义 |
|------|------|
| MoE | 混合专家模型，用多个 FFN 专家替换单个 FFN |
| Router | 路由器，计算 Token 与专家的匹配得分 |
| Top-$k$ | 每 Token 只激活得分最高的 $k$ 个专家 |
| 共享专家 | 每个 Token 强制激活的专家，吸收共性知识 |
| 路由崩溃 | 少数专家承载所有 Token，其余专家闲置 |
| 负载均衡损失 | $\mathcal{L}_{\text{lbl}} = \frac{E}{k} \sum f_e P_e$，防止路由崩溃 |
| 专家并行（EP） | 将不同专家分布到不同 GPU，通过 All-to-All 通信 |
| All-to-All | 分布式通信算子，每张 GPU 与其他所有 GPU 交换数据 |
| GroupedGEMM | 单算子同时处理多组维度不同的矩阵乘法 |
| 路由翻转 | 边界处因微小扰动导致选中专家突变 |
| ReMoE | 用 ReLU 替代 Top-$k$+Softmax 实现平滑连续路由 |


## 2. 压缩、智能与预测

将语言模型的任务视为**无损压缩**。预测能力与压缩能力等价。

训练即最小化交叉熵 $\sum_t -\log_2 p_\theta(x_t \mid x_{<t})$，等价于最大化压缩比。

### 2.1 两部分无损描述

$$
L_{\text{total}} = L_{\text{model}} + \sum_t -\log_2 p_{\theta}(x_t \mid x_{<t})
$$

- **$L_{\text{model}}$**：模型参数的比特数。
- **残差代码长度**：给定模型下数据的编码长度。

### 2.2 压缩比实例

假设原始数据 510 Tbits，模型权重 6.4 Tbits，残差 30 Tbits：$L_{\text{total}} = 36.4$ Tbits，压缩比 $\frac{510}{36.4} \approx 14$ 倍。

#### 算术编码示例

编码字符串 `hello`，模型预测 $p(h)=0.4, p(e)=0.2, p(l)=0.3, p(o)=0.1$：

1. $[0,1)$ 按概率分成 $h=[0,0.4), e=[0.4,0.6), l=[0.6,0.9), o=[0.9,1)$，`h` 落 $[0,0.4)$。
2. 在 $[0,0.4)$ 内按 $p(e)=0.5, p(l)=0.3, p(o)=0.2$ 细分，`e` 落 $[0,0.2)$。
3. 逐 token 进行，最终缩至唯一二进制小数表示整个序列。

解码同理：收到比特串 → 用模型划分区间 → 看落在哪个区间即得 token。每步只需一次前向传播获取概率分布，无需搜索。

### 2.3 柯尔莫哥洛夫复杂性

$$
K_U(x) = \min_{p: U(p)=x} \vert{}p\vert{}
$$

一个字符串 $x$ 的柯氏复杂性，是指通用图灵机 $U$ 上能输出 $x$ 的**最短程序 $p$ 的长度**。

- 数据有规律 → 生成程序可以很短 → 低柯氏复杂性。
- 数据随机 → 最短程序只能"逐字死记硬背" → 高柯氏复杂性。

| 类型 | 数据 | 最短程序 | 柯氏复杂度 |
|:----|:----|:--------|:---------|
| 算法序列 | `AB AB AB AB AB` | `repeat "AB" 5 times` | 低 |
| 无结构序列 | `Q7 B2 M9 X4 C1` | `store Q7B2M9X4C1` | 高（≈ 数据长度）|

自然语言蕴含物理规律、语法、因果关系。将几百 TBits 的知识压缩到几百亿参数中：
1. **死记硬背行不通**——参数远小于训练数据。
2. **被迫理解规律**——模型必须在参数内部构建数据的底层规律。

> 大模型为完成"极致压缩"，在数学上被迫发现并模拟世界的**生成器**——即智能。


## 3. 对齐与后训练（Post-training）

### 3.1 预训练的局限

预训练目标 $-\log p(x_t \mid x_{<t})$ 是"哑巴"统计镜像——学会文本中的一切（包括错误和偏见），需要从"统计上可能"过渡到"实际有用"。

### 3.2 对齐阶梯

| 阶段 | 核心问题 |
|:----|:--------|
| **1. 预训练** | 下一个 token 可能是什么？ |
| **2. 监督微调（SFT）** | 针对这个指令，好的回复是什么样的？ |
| **3. 偏好优化** | 哪个回复更符合人类偏好？ |

三个阶段都训练**同一个 next-token 预测器**，只是使用不同类型的示例和反馈。

### 3.3 SFT 训练

SFT 数据集包含异构任务（分类、头脑风暴、创意写作等），迫使模型根据上下文切换角色：

$$
\mathcal{L}_{\text{SFT}} = - \sum_{t \in \text{response}} \log p_{\theta}(y_t \mid c, y_{<t})
$$

**关键**：Loss 只对 `response` 部分计算，不对 Prompt 计算（Prompt 的 Label 设为 `-100` 忽略）。前向传播完整读取 Prompt 获取上下文，反向传播仅更新 Response 路径。

### 3.4 偏好优化

**训练奖励模型**：对同一 prompt $x$，策略生成 $K$ 个回复 $y_1, \dots, y_K$，标注者排序 $y_{(1)} \succ y_{(2)} \succ \dots$。奖励模型学习预测标注者更偏好哪个输出。

| 维度 | SFT | 偏好反馈（RLHF） |
|:----|:-----|:----------------|
| 输入数据 | 提示 + 人工标注演示 | 提示 + 多个策略输出 |
| 反馈 | 复制标注答案 | 标注者对输出排序 |
| 训练目标 | 增大演示 token 概率 | 训练 RM 预测偏好 |

**PPO 优化策略**：

1. **采样**：给模型一个 prompt，让它生成回复。
2. **打分**：奖励模型对回复打分——分数越高，表示越符合人类偏好。
3. **更新**：用分数调整模型参数——分数高的回复，提高它对应 token 的生成概率；分数低的则降低。同时加一个 KL 惩罚，防止模型为了高分而胡乱生成（偏离 SFT 太远）。

> 这就是 RLHF-PPO 的完整流程：RLHF 是整体框架（用人类反馈训练奖励模型 → 用奖励模型指导策略优化），PPO 是第三步中用来更新策略的具体强化学习算法。
3. **更新**：PPO 增大期望奖励，同时施加惩罚防止偏离 SFT 过远。

> 预训练使模型**渊博**，后训练使其**有用**。


## 4. 前沿能力

### 4.1 思维链（Chain-of-Thought）

| 维度 | 标准提示 | Chain-of-Thought |
|:----|:--------|:----------------|
| 方法 | 输入 → 直接输出答案 | 输入 → 分解推理步骤 → 答案 |
| 效果 | 无法正确计算 | 暴露中间计算，成功得出正确答案 |

生成中间 token 使模型能计算并暴露后续答案所依赖的精确上下文，大幅提高推理准确率。

### 4.2 In-Context Learning（上下文学习）

LLM 可通过提示中的少样本示例，将概念映射到**任意、非标准**的标签，无需修改模型权重。

示例：要求模型将情感映射到**自定义**标签 `dax` / `mip`：

| 文本 | 隐含情感 | 映射标签 |
|:----|:--------|:--------|
| "The battery lasts all day." | positive | **`dax`** |
| "The screen cracked immediately." | negative | **`mip`** |

- **推理**：输入 `"Setup was easy and the camera is sharp."` → 模型识别为 positive → 输出 **`dax`**。
- **零权重更新**：完全在推理时完成，无需梯度更新。

模型不仅能依赖预训练的语义定义，还能仅从上下文覆盖已有关联，学习全新的语义到标签映射。
